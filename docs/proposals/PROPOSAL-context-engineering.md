ასეთი მეთოდოლოგია არსებობს და დარგში დღეს მას **context engineering** ჰქვია. მას Anthropic აღწერს, მაგალითად სტატიებში „Effective context engineering for AI agents“ და „Building effective agents“, ასევე Manus და სხვა ლიდერები, ვინც agent-ებს მასშტაბზე ამუშავებს.

მისი მთავარი დასკვნა ჩვენთვის გადამწყვეტია: **კონტექსტის შემცირება ხარისხს არ წევს, პირიქით, ზრდის.** კვლევები აჩვენებს, რომ კონტექსტი რაც უფრო იზრდება, მით უფრო უარესდება მოდელის ყურადღება (ამას „context rot“ ჰქვია). 18 KB-იანი კანონების წაკითხვის შემდეგ agent-ს მთავარი უფრო ცუდად ახსოვს, ვიდრე 3 KB-იანი ბარათის შემდეგ. ამიტომ „ხარისხი ან ეკონომია“ ცრუ არჩევანია: ორივეს ერთი და იგივე მოქმედება გვაძლევს, ანუ ხმაურის მოცილება.

ქვემოთ ჩემი გადაწყვეტილებაა, თქვენ მიერ ჩამოთვლილი თითოეული განზომილებით.

## 1. პრინციპი: ყველა token-მა თავისი ადგილი უნდა გაამართლოს

კონტექსტი ბიუჯეტია და არა საწყობი. agent-მა უნდა მიიღოს **ყველაზე მცირე ოდენობის ყველაზე ღირებული ინფორმაცია**, რომელიც ამ ნაბიჯისთვის სჭირდება. ფორმულა მარტივია: **ხარჯი = კონტექსტის ზომა × ნაბიჯების რაოდენობა.** შესაბამისად ორი ბერკეტი გვაქვს: კონტექსტი იყოს პატარა და ნაბიჯები ცოტა.

## 2. კონცეფცია: დაამოწმე, ნუ ასწავლი

ეს ყველაზე ძლიერი ბერკეტია და დღეს საერთოდ არ ვიყენებთ. თუ წესს ავტომატური შემოწმება (gate) იცავს, მისი ტექსტი agent-მა წინასწარ **საერთოდ არ უნდა წაიკითხოს**. დაარღვევს, gate გააჩერებს, და შეცდომის ტექსტი ზუსტად იმ მომენტში ასწავლის წესს. მაგალითად, dependency arrow-ს ESLint იცავს, ამიტომ მისი აღწერა ჩატვირთვაში ზედმეტია. gate-ს ყოველ ჩატვირთვაზე 0 token უჯდება, პროზას კი ყოველ ნაბიჯზე.

**დასკვნა:** ჩატვირთვაში რჩება მხოლოდ ის, რისი მექანიზაციაც შეუძლებელია: განსჯა, იდენტობა და კარდინალები.

## 3. არქიტექტურა: ცოდნა ფენებად, საჭიროებისას ჩატვირთვით

ფენების იდეა Anthropic-ის Skills-ის პრინციპიდან მოდის.

| ფენა | რა არის | ლიმიტი | როდის იტვირთება |
|---|---|---|---|
| **L0** | კარდინალები თითო ხაზზე, თითო ტესტით + რუკა | ≤3k | ყოველთვის, ყველასთვის ერთნაირად |
| **L1** | როლის ბარათი | ≤1k | ყოველთვის, მხოლოდ ამ როლს |
| **L2** | ცოდნის ბარათები: პატერნი, გრამატიკა, რეკომენდაცია | ≤1k თითო | მხოლოდ საჭიროებისას, სახელით |
| **L3** | ADR-ები, აუდიტები, ისტორია | — | არასოდეს ჩატვირთვისას, მხოლოდ მითითებით |

ჯამში ჩატვირთვა ≤5k გამოდის ჩვენი ტექსტიდან. ჯაჭვი ლოგიკურად ვითარდება: **კარდინალი → კანონი (მისი კონკრეტული მიბმა) → gate (მისი ავტომატური დაცვა) → ბარათი (როგორ გამოიყენო) → ADR (რატომ).** ყოველ რგოლს ერთი სახლი აქვს და ზედა რგოლი ქვედაზე მიუთითებს, მისი გადაწერის ნაცვლად.

## 4. ტექნიკა: cache-ის შენარჩუნება

Claude Code ხშირად გამეორებულ ტექსტს ავტომატურად ინახავს (prompt cache). შენახული ნაწილის ხელახლა წაკითხვა ჩვეულებრივ ფასზე დაახლოებით 10-ჯერ იაფია. Manus-ის ინჟინრები ამ მაჩვენებელს ყველაზე მნიშვნელოვნად მიიჩნევენ.

წესი ასეთია: დასაწყისი ყველა agent-ისთვის ბაიტ-ბაიტ იდენტური და უცვლელი უნდა იყოს, ცვალებადი ტექსტი კი ბოლოში. ჩვენი hook-ები ამჟამად დასაწყისშივე ცვალებად ტექსტს ამატებენ, მაგალითად session router-ი და mode, და ამით სავარაუდოდ cache-ს არღვევენ. ეს გადასამოწმებელია და, თუ დადასტურდა, უფასოდ გამოსასწორებელი.

## 5. ლოჯისტიკა: ვინ, სად, რით

- **სამუშაო იქ ხდება, სადაც კოდია.** framework-ს თავისი სესია აქვს, national-accounts-ს თავისი. დღევანდელი 133k ამ წესის დარღვევის ფასია.
- **დავალება ფაქტებს შეიცავს და არა მითითებებს.** ორკესტრატორი, რომელმაც ფაქტები უკვე იცის, agent-ს აძლევს მზა შეჯამებას და ზუსტ მისამართებს `file:line` ფორმით. agent-ი სხვის მიერ უკვე შესრულებულ ძებნას თავიდან აღარ იწყებს.
- **agent-ის გაშვება მხოლოდ მაშინ ღირს, როცა მისი ცალკე კონტექსტი სარგებელს მოაქვს.** მცირე საქმეს ადგილზე ვაკეთებ.
- **agent-ი მინიმალური ხელსაწყოებით მუშაობს.** chief-engineer-ს ახლა Playwright და Chrome DevTools მუდმივად თან აქვს, ყოველ ნაბიჯზე ათასობით token-ად. ხელსაწყო მხოლოდ იმ დავალებას უნდა მიეცეს, რომელსაც ის სჭირდება.
- **agent-ი მოკლე პასუხს აბრუნებს, ≤1–2k.** სრული შედეგი ფაილშია და არა ჩატში.
- **სამუშაოს ტიპს შესაბამისი მოდელი ემთხვევა.** მექანიკურ საქმეს იაფი მოდელი აკეთებს, განსჯას ძლიერი.

## 6. სტრატეგია: წესების ბიუჯეტი და გაზომვა

ეს ნაწილი იმას აგვარებს, რის გამოც პრობლემა დღემდე ვერ აღმოიფხვრა.

- **ფიქსირებული ბიუჯეტი.** L0-ს ლიმიტი აქვს და `render.py --check` ცვლილებას ავტომატურად დაბლოკავს, თუ ლიმიტი გადაჭარბდა. ახალი წესის დასამატებლად ძველი უნდა ამოიღო ან gate-ში გადაიტანო. ასე სისტემა ფიზიკურად ვეღარ გაიბერება, და ეს დისციპლინაზე კი არა, მექანიზმზე დგას.
- **გაზომვა ყოველ გაშვებაზე.** ვზომავთ ჩატვირთვის token-ებს, ნაბიჯების რაოდენობას, cache-ის წილს და ყველაზე მთავარს: რამდენი token დაიხარჯა ერთ რეალურ ცვლილებაზე. თუ გაშვებამ 60k წაიკითხა და ერთი ფაილიც არ შეცვალა, ეს ავტომატურად ფიქსირდება.
- **ადრეული შემოწმება.** agent-მა N ნაბიჯში უნდა აჩვენოს ან პირველი ცვლილება, ან თავისი გეგმა. თუ ვერ აჩვენა, ჩერდება და ანგარიშს აბრუნებს, ტყუილად კითხვას აღარ აგრძელებს.
- **დაგროვილის გაწმენდა.** 2.6 MB ცოდნა და 6.2 MB დოკუმენტაცია ან მოკლე შეჯამებად გადაიქცევა, ან არქივში გადავა. 30 დღე გამოუყენებელი მექანიზმი იშლება, როგორც ეს უკვე წესადაა დადგენილი.

## 7. ხარისხის გარანტია: ორი ღონისძიება

1. **დაკარგვის საწინააღმდეგო ცხრილი.** ძველი ტექსტის ყველა წესი ან ახალ სახლში გადადის, ან gate-ში, ან შეგნებულად იშლება მიზეზის მითითებით. ცხრილს მეორე, დამოუკიდებელი agent ამოწმებს.
2. **შეფასება რეალურ ამოცანებზე (evals).** ეს დარგის სტანდარტია და Anthropic ამას გადამწყვეტად მიიჩნევს. ვიღებთ 5–8 რეალურ, უკვე შესრულებულ ამოცანას, ვუშვებთ ძველ და ახალ სისტემაზე და ვადარებთ შედეგსა და ხარჯს. „ხარისხი არ დაეცა“ ასე მტკიცებულებად იქცევა და აღარ არის უბრალო განცხადება.

## რიგი

1. **ახლავე, უფასოდ.** L3a-ს იმ სესიაში ვაკეთებთ, რომელიც agent-framework-შია გახსნილი. ჩემი მხრიდან ყოველ დავალებაში ფაქტებს თავად ჩავწერ.
2. **საწყისი მდგომარეობის გაზომვა.** რეალურად რამდენს იხდის ახლა თითო ტიპის agent ჩატვირთვაზე და თითო გაშვებაზე, და მუშაობს თუ არა cache. ყველაფერი დანარჩენი ამ ციფრებს დაეყრდნობა.
3. **ADR framework-ში.** ზემოთ აღწერილი ფორმა ოფიციალურად დადგინდება, უარყოფილი ალტერნატივების დასაბუთებით. ეს framework-ის ძირითადი, ძნელად შესაცვლელი გადაწყვეტილებაა, ამიტომ მას ყველაზე ძლიერი agent დაწერს.
4. **კომპაქტიზაცია kit-ში.** მოიცავს დაკარგვის საწინააღმდეგო ცხრილს, ზომის gate-ს და cache-ის შესწორებას.
5. **Evals.** ძველი და ახალი სისტემა შედარდება რეალურ ამოცანებზე.
6. **L3b → C → მიგრაცია** უკვე კომპაქტურ ფორმაზე. მიგრაციის ბოლოს ძველი ფაილები იშლება.

**რას ველი შედეგად:** ჩატვირთვა ~20k+-დან ≤5k-მდე ჩვენს ნაწილში, ხოლო ტიპური გაშვება 100k+-დან 30–40k-მდე. ზუსტ ციფრებს მე-2 ნაბიჯი დაადასტურებს ან შეასწორებს. ხარისხს მე-5 ნაბიჯი დაამტკიცებს.

ერთი რამ თქვენზეა დამოკიდებული: L3a-სთვის გახსენით სესია agent-framework-ში. დანარჩენ ნაბიჯებს მე წავიყვან.
